## Concrete bounded improvement completed

The audited `SpatialSession.observe` constructed a `SpatialSample` plus wheel-angle/velocity tuples on every 500 Hz callback, then discarded it on nine of ten callbacks. Construction now occurs only when `sequence % 10 == 0`; the original 500 Hz attitude update and visual callback position remain. The existing mixed14s physical regression in `results/session_20261023/spatial/dto_allocation_v1/summary.json` records 7,000 observe calls, 700 DTO constructions and 7,001 attitude updates including startup. All 7,000 control-history rows and 700 published source DTOs are exact against the preserved baseline. The old construction count is inferred from the hash-checked source, not falsely presented as a new measurement. This removes known unused allocations without adding an algorithm or module; no isolated latency improvement is claimed.

## Profiling evidence must not be overstated

The earlier instrumented fixed 20 s cancel/resume fixture records 10,000 estimator/control updates, 20,000 native MuJoCo steps and derived-sensor refreshes, and 10,001 SpatialAttitude updates. These observations establish actual call paths/frequencies, not the fraction of uninstrumented CPU that would be removed by a new migration.

A read-only consistency check found five records in `profile/native/profile.pstats` and seven in `profile/python_oracle/profile.pstats` with cumulative time smaller than self time or zero primitive-call count despite positive total calls. For example, `ideal_imu_measurement` shows 20,000 total calls but zero primitive calls/cumulative time. `profile_integrity_review.json` retains exact records and SHA256. The cause has not been established; do not invent one or derive precise cumulative CPU percentages from these artifacts. Use them as qualitative locators, and use independent explicit per-call wall/thread probes and fair uninstrumented runs for quantitative conclusions.

The v2 production reference microbenchmark kept equivalent per-call latency and throughput windows, but sampled process rusage after restoring GC. This could include cleanup CPU outside its wall window. It remains preserved evidence for its measured latency/wire results and is superseded for process CPU claims by v3, whose rusage endpoint is captured before GC/profiler/file cleanup. CPU and wall in WSL remain host software measurements. Profile/tracemalloc diagnostics are never pooled with performance runs.

## Build and owner consistency

Both follow and simulation `package.xml` now declare `ament_cmake`; CMake creates the actual native modules/libraries and configured simulation entry scripts. Existing setuptools files remain relevant to editable Python package discovery, but they do not compile or replace the native owners. The import shims require the current workspace's installed native module and provide no Python motion fallback. The benchmark verifies its loaded native library through `/proc/self/maps` against the current workspace artifact and hashes source/config/library identities.

The formal `spatial_state` executable resolves to `ros2_ws/build/companionbot_control/spatial_state` via its install symlink. The compatibility Python module dispatches that installed ELF. There is one spatial ROS state owner, one motion authority, one active TwoPathProducer policy, and the unchanged separate C99 MCU safety authority. Mapping/offline test oracles are not advertised as a second production chain. No physical arm or hardware-readiness claim follows from successful host builds or tests.
